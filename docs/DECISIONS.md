# Decisions

Format: date · decision · rationale · alternatives. Newest at the bottom. Context: `docs/STATUS_AUDIT.md`, spec: `docs/SPEC.md`.

| ID | Date | Decision | Rationale | Alternatives considered |
|---|---|---|---|---|
| D-1 | 2026-10-10 | **Goal: real users soon.** Store compliance, accounts and privacy come before new features. | The demo has no accounts, leaked keys and fake data shown as real (STATUS_AUDIT §2); none of that survives contact with real users or store review. | Keep polishing the hackathon demo; add features first. |
| D-2 | 2026-10-10 | **v1 = extension-first:** Chrome extension + small web dashboard (Expo web build) + backend. Mobile companion moves to v1.1. | The extension is where drift detection and recovery actually happen; one surface ships sooner and keeps more data on-device. | Mobile + extension together (SPEC's original "Now" roadmap). |
| D-3 | 2026-10-10 | **Momentum rule:** a long unbroken stretch inside the active context makes grace **shorter** if the user drifts (high momentum → ~120s floor). Deep focus never earns extra grace. Momentum = time inside the context, not "no tab switches". | Catch drift before momentum is lost. The old SPEC §9.4 rule (`> 45 min → ×1.25`) rewarded focus with slack exactly when a detour is costliest. Measuring "no switches" would read 2 h on one YouTube tab as deep focus. | `momentum_factor × 1.25` (old README 1 §9.4); team's earlier momentum × baseline × risk matrix. |
| D-4 | 2026-10-10 | **Snooze-adaptive grace: deferred to v1.1.** v1 ships fixed grace + manual setting. When built: ask don't adjust, count only snoozes ending in self-return, per destination, cap 15 min, decay (SPEC §9.4.1). | Silently learning from snoozes learns from avoidance and ratchets toward never nudging; also breaks P2 and "explainable and reversible". Needs outcome metrics first. | Auto-raise grace when a user always snoozes (original proposal). |
| D-5 | 2026-10-10 | **Android app-blocker module archived** to branch `archive/android-blocker` and removed from the main line. | Outside spec scope (mobile does not observe other apps), Play policy risk (`QUERY_ALL_PACKAGES`, wrong FGS type), and `startActivity` from a background service likely does nothing on Android 10+. | Fix it (overlay / full-screen intent / AccessibilityService); keep it in-tree disabled. |
| D-6 | 2026-10-10 | **Leaked API keys revoked** rather than rewriting git history. | Repo is private; revoking makes the leaked keys worthless; a history rewrite would force every teammate to re-clone and disrupt in-flight work. | `git filter-repo` / BFG history scrub + force-push. |
| D-7 | 2026-10-10 | **Demo data only behind flags:** backend `DEMO_MODE=true` (seed data, mock fallbacks) and app `EXPO_PUBLIC_DEMO_MODE=1` (client mock fallback). Default is off: honest empty/offline states. | Silent mock fallback showed fake streaks and lost real writes (STATUS_AUDIT §2.4). | Delete mocks entirely; keep silent fallback. |
| D-8 | 2026-10-10 | **Moved to `krimy-7/focusguard` (public), history scrubbed.** Leaked keys/password replaced in every commit of the new repo; authorship kept. Krishna Nishad (KriMPie) is the sole active maintainer; the other three Team MindMess members contributed during the hackathon only. Supersedes D-6 for the new repo (D-6 still describes the old hackathon repo). | Product needs a repo the team controls; going public makes history scrubbing mandatory, and a fresh repo means no teammate disruption. | Keep working in the hackathon org repo; push history unscrubbed; single fresh commit (loses credit). |
| D-9 | 2026-10-10 | **Detect-first contexts** (SPEC §7): the extension observes continuously within the privacy floor, proposes a context from activity, soft-confirms after 90s; user can edit/cancel. | The researched product promise is that the user doesn't have to manage it; detection is the differentiator. | Declare-first (proposal PDF); declare-first with suggested name. |
| D-10 | 2026-10-10 | **AI = bring your own key.** FocusGuard runs no LLM. The key is stored only in the extension and calls go straight from the extension to the user's chosen provider (with clear disclosure). Without a key everything works on rules; Chrome on-device Gemini Nano is the free middle tier where available. The backend holds no AI keys. | Original team plan; zero AI cost; server never sees what goes to an LLM. Rules must be good enough because most target users won't have a key. | Hosted LLM paid by FocusGuard; keys stored server-side. |
| D-11 | 2026-10-10 | **Planning without AI in v1:** goals are typed (one per line, simple splitter). AI planning/voice moves to v1.1. | Keeps the key in one place (the extension); least code; voice planning belongs to the mobile companion. | Dashboard asks the extension to run AI; separate key per device. |
| D-12 | 2026-10-10 | **Engine runs in the extension (Q-1), pending engine-design review.** Server = accounts, goals, settings, compact summaries, later mobile relay. | Follows from D-9 + D-10: detection, the AI call, timers and nudges all live in the browser; less data leaves the device. | Server-authoritative engine (old SPEC §5/§17). |
| D-13 | 2026-10-10 | **First users: students and developers in Nepal/India, English UI** (Nepali copy later, SPEC §22). | Reachable audience for a solo maintainer. Consequences: day boundaries in the user's local tz (UTC+5:45 / +5:30), backend hosted near South Asia, sensitive list covers local banks/wallets/gov portals. | English + Nepali at launch; global audience first. |
| D-14 | 2026-10-10 | **AI options in the extension:** Off (default, rules) · On-device (Chrome Gemini Nano) · Local model (Ollama/LM Studio on localhost) · Your API key. Only the last sends anything off the machine (hostname + sanitized title + context name, to the user's provider). | Extends D-10 so privacy-maximalists can keep AI fully local. | Cloud key only. |
| D-15 | 2026-10-10 | **Architecture (design §1):** extension does the work; backend stores goals, contexts (name, mode, state, site *names*), settings, daily totals. Page titles, URLs, raw events, resume targets and AI keys never leave the browser. REST only in v1 (no WebSockets). Auth: Supabase Auth (email code + Google), FastAPI verifies JWTs via JWKS; extension signs in separately. | A privacy claim that is literally true; removes the raw-event purge job; research in `docs/research/2026-10-10-auth-hosting.md`. | Server-authoritative engine with 7-day raw retention (old SPEC §15). |
| D-16 | 2026-10-10 | **Hosting: $0 budget.** FastAPI container on Google Cloud Run free tier (Mumbai, max 1 instance, $1 budget alert) + Supabase free Postgres (Mumbai). Nightly `pg_dump` via GitHub Actions because the free plan has no backups. | Maintainer has a card but will not spend money; container keeps Railway/Oracle as drop-in fallbacks. | Railway $5/mo; Oracle Always Free VPS. |
